audio_output.ts

Sends an AudioContext's sound, or a media element's, to a chosen output device.

Browsers differ, so each route is feature-detected, never sniffed:

  • context — the context itself takes a sink (AudioContext.setSinkId, Chromium). Lowest delay, nothing extra in the graph.
  • element — the context can't, but media elements can (HTMLMediaElement.setSinkId, Firefox): the context plays into a MediaStreamAudioDestinationNode whose stream an <audio> element plays on the chosen device. Adds the element's buffering. The element's play() comes after await setSinkId, past a click's transient activation, so this route relies on the page's sticky activation: the person has already interacted with it, as the Join click that unlocks a call's context does. Without that the browser's autoplay policy refuses the audible element, which reads as play_refused.
  • default — the system default, straight from the context. Safari offers no output choice, so it only ever has this one.

create_audio_output
#

audio_output.ts view source

create_audio_output(context: AudioContext, sink_id: string, deps?: AudioOutputDeps): Promise<AudioOutput>

Routes context to the output device sink_id, the empty string being the system default. A context that takes a sink is set back to the default for the empty string too, so switching back works.

import {create_audio_output} from '@fuzdev/fuz_ui/audio_output.ts';

parameters

context
: AudioContext
#

sink_id
: string
#

deps
?: AudioOutputDeps = create_audio_output_deps()
#

returns

the node to connect sound to, its route, and a close for it

throws

  • DOMException - when the browser refuses the device, or NotSupportedError when no route can reach a non-default device
  • Error - named MEDIA_PLAY_REFUSED_ERROR_NAME when the element route's play() is refused as autoplay, with the browser's error as its cause; call it from a page the person has interacted with
