remote_audio.svelte.ts

Plays the remote streams of a call through one AudioContext, with a volume and mute per stream.

Why one context, unlocked in a click. A phone's browser plays audio only once a gesture has allowed it. A fresh <audio> per peer can't play a peer who arrives later, with no tap in between: its play() is refused. One context resumed inside a click (unlock, in the Join handler) plays every stream routed into it afterwards, however late it arrives. So each stream goes MediaStreamAudioSourceNode → its own GainNode → the output, and nothing plays through a per-peer element.

The helper element. Chromium pulls a remote WebRTC stream into Web Audio only while a media element holds it, so each stream also gets a muted <audio> that plays nothing anyone hears. Safari doesn't need it and isn't harmed by it; helper_elements: false drops it.

Suspended again. A phone call or backgrounding the page suspends the context (suspended, or interrupted where the browser says so), and only a later gesture is sure to resume it. needs_resume is then true, for a quiet "tap to hear the room" that calls resume from its click.

Output device. set_output uses AudioContext.setSinkId where the browser has it, routes through an element where only media elements take a sink, and otherwise stays on the default output (can_choose_output is then false). See audio_output.ts.

The remote half of a call's audio. Construct it anywhere (it touches no browser API until unlock), call unlock from the click that joins, then add each remote stream as it arrives and remove it when it leaves. Streams added before unlock start playing at unlock.

unlock
(): Promise<void>
#

Opens the context if there isn't one, and resumes it. Call it synchronously from a click (the Join handler), before any await: the browser allows playback only inside the gesture. Resolves once the browser has answered; status says how, and stays as it was until then. A context the browser closed is replaced by a fresh one, with every stream and the output device carried over.

resume
(): Promise<void>
#

Resumes a paused context from a later gesture, as needs_resume asks. Does nothing before the first unlock or after close, so a stray prompt can't start playback early. Also safe to try without a gesture (on returning to the page): some browsers allow it, and the rest leave needs_resume set.

set_output
(device_id: string): Promise<RemoteAudioOutputResult>
#

Sends the call to the output device device_id, the empty string for the default. Before unlock, or once the browser closed the context (before or during the change), it's kept and applied at the next unlock. A failure sets output_error and leaves output_device_id on the device sound still plays on, except where a superseded change lands after the failure. A change superseded by a later one resolves aborted if it landed, or with its own refusal if it didn't.

close
(): void
#

Stops everything: the streams, the output route, and the context. Volumes and mutes are kept, and a later unlock opens a fresh context.
